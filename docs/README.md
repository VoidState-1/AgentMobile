## 1. 文档范围

本目录描述 Agent Mobile 当前代码的结构、接口、持久化、运行机制与维护方法。产品设想、阶段计划、外部评审和历史验收记录保存在 [Design](../Design/)，不能直接作为当前实现的依据。

本套文档属于新的稳定技术文档系列，初始版本统一为 `1.0.0`。稳定表示围绕长期维护组织内容，并不表示产品已发布、接口不会改变或全部平台均已验收。当前项目允许破坏性更新；接口和数据格式变化时应同时更新调用者、测试和相关文档。

事实依据优先级为：当前源码与锁文件 → 当前可复现的测试结果 → 本目录说明 → Design 中的历史资料。出现不一致时先核对源码和测试，再修正文档，不为文档里的旧约定增加代码兼容层。

## 3. 推荐阅读顺序

首次参与开发：系统设计 → 开发环境 → 应用接口 → 自己负责的子系统 → 测试与维护。

排查文件丢失、Git 异常或重启问题：存储与恢复 → 工作区与 Git → 对话与轨迹 → 测试与维护。

新增模型、工具或子 Agent：Agent 执行 → 相应集成文档 → 应用接口 → 存储与恢复。先明确副作用、授权和回执，再扩展 UI。

## 4. 更新历史格式

每份文档的一级标题之后、正文之前放置本文件相同的历史表。新记录追加到表格顶部，保留已有记录；同一次未提交的编辑可合并为一条记录。字段含义如下：

- **文档版本**：使用 `MAJOR.MINOR.PATCH`；重组结构或改变核心契约升主版本，补充重要能力升次版本，修正说明升补丁版本。它独立于应用版本、数据库格式和 SDK 版本。
- **更新时间**：ISO 8601 格式并含时区，例如 `2026-10-15T17:22:27+08:00`。表示文档实际更新的时间，不使用 Git 提交作者时间替代。
- **最新 Git 提交 ID**：编辑时执行 `git rev-parse HEAD` 得到的完整提交 ID，表示已提交代码基线。若文档同时描述尚未提交的源码变化，在变更说明明确注明；合入后再更新基线记录。
- **内容变化**：说明改动的技术范围，例如“补充 MCP unknown 回执恢复”，避免只有“更新文档”。

Git ID 不是本文档将来提交的 ID，也不要求文档通过引用自身提交形成循环。追溯某版文档的实际修改可使用 `git log --follow -- docs/<文件名>`；查看代码基线可使用 `git show <提交ID>:src/<路径>`。

## 5. 编写与同步规则

正文统一使用中文，代码标识符和接口名保持源码中的英文。仓库内链接使用相对路径，避免开发机绝对路径。源码链接指向文件，不复制容易失效的行号。

技术文档应包含责任边界、数据或接口契约、关键流程、故障行为、限制及源码/测试入口。复用其他文档的详细说明时使用链接；常量和 schema 以其所属文档为维护入口，不在每篇重复整张表。

能力状态用明确描述：**已实现**是当前存在调用链，**已有验证**需要指出测试类型和平台，**尚未实现**不能写成现成功能。模拟协议通过不代表供应商真服务通过；Web 通过不代表 Hermes、SecureStore 或原生进程恢复通过。

文档变更至少检查：历史字段完整、链接可达、示例与现有 API 一致、无凭证或私有资料、未把 Design 的历史结论当成当前测试。修改后执行 `npm run check`；文档排版执行 `npx prettier --check docs README.md`。测试结果只记录实际执行的项目，不套用旧验收数量。

## 6. 与其他仓库文件的关系

[根 README](../README.md) 是项目介绍和快速启动入口；[AGENTS.md](../AGENTS.md) 是开发约束；[package-lock.json](../package-lock.json) 是安装版本依据。[Design](../Design/) 保留历史，不纳入本目录“当前事实”的维护责任。

设计范围与实施状态以 [design.md](design.md) 为汇总入口。详细契约变化同时修改对应主题文档，避免只在索引或阶段报告中记一句“已完成”。
